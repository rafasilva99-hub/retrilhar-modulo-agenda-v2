Os 3 Problemas Reais (e por que acontecem)

Problema 1: IA não entende mudanças do produto, docs ficam desatualizados

Causa raiz: CLAUDE.md é tratado como "escreve uma vez e esquece". O modelo lê essa documentação toda sessão, mas se ela não reflete o estado atual, o resultado diverge. É como dar um mapa de 2024 pra alguém dirigir em 2026.

Problema 2: Frontend despadronizado apesar de mil regras

Causa raiz: Regras demais = regras ignoradas. A Anthropic documentou isso oficialmente: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." Além disso, regras textuais são sugestões — não são garantias. A IA pode "decidir" que outro padrão faz mais sentido e ignorar sua instrução.

Problema 3: Gaps de integração frontend-backend

Causa raiz: Front e back estão trabalhando contra contratos diferentes (ou sem contrato nenhum). O front usa dados mock que não batem com a API real. Os testes passam isolados porque testam contra mocks — não contra o schema real.

# Retrilhar Admin Panel v2

## Stack
- Next.js 16 (App Router) + React 19 + TypeScript strict
- Tailwind CSS 4 (CSS-first config, NO tailwind.config)
- shadcn/ui (components/ui/) — NUNCA recrie, use `npx shadcn@latest add`
- HugeIcons (icon font CDN) — ver .claude/rules/icons.md para nomes válidos

## Comandos
- `pnpm dev` — dev server
- `pnpm build` — build (DEVE passar sem erros antes de commitar)
- `pnpm lint` — ESLint
- `pnpm typecheck` — TypeScript strict

## Regras Inegociáveis
- NUNCA use hex/rgb hardcoded. Use classes Tailwind ou CSS variables de globals.css
- NUNCA crie componente que já existe em components/ui/ ou components/custom/
- NUNCA invente nomes de ícones. Consulte .claude/rules/icons.md
- NUNCA use lucide-react fora de components/ui/. No app, use <Icon name="...">
- ANTES de criar qualquer componente, verifique: ls components/custom/ components/ui/

## Contracts
- Tipos de API ficam em types/api/. O frontend CONSOME esses tipos, nunca cria tipos soltos
- Dados mock DEVEM seguir o schema de types/api/. Ver docs/API_CONTRACTS.md
- Se a API mudou, PRIMEIRO atualize types/api/, DEPOIS ajuste os componentes

## Quando compactar
- Preserve: lista de arquivos modificados, comandos de teste, decisões de arquitetura
- Descarte: outputs longos de lint, conteúdo completo de arquivos lidos

Por que ≤100 linhas? Pesquisa da comunidade mostra que modelos frontier seguem ~150-200 instruções com consistência. Cada linha a mais compete pela atenção. Se o CLAUDE.md tem 300 linhas, as regras do meio são efetivamente invisíveis.

Rules com Path Scoping — O Game Changer

A mágica do scoping: regras só carregam quando o Claude está mexendo nos arquivos que batem com os paths. Isso significa que quando ele está trabalhando numa página de vendas, ele NÃO recebe as regras de layout do shell — e vice-versa. Exemplo: .claude/rules/components.md

# Contracts de API

## Fonte de verdade
- Schemas da API ficam em types/api/. Isso é o CONTRATO.
- Se o backend muda, types/api/ muda PRIMEIRO.
- Componentes e hooks CONSOMEM esses tipos — nunca criam tipos inline.

## Checklist para qualquer integração
1. O tipo existe em types/api/? Se não, PARE e crie primeiro.
2. O mock em __mocks__/ bate com o schema? Verifique campos obrigatórios.
3. O hook usa o tipo correto de types/api/? Sem `any`, sem tipo inline.
4. O componente consome via hook (nunca fetch direto)?

## Quando a API muda
1. Atualize types/api/[entidade].ts
2. Rode pnpm typecheck — vai quebrar onde precisa atualizar
3. Atualize hooks/use[Entidade].ts
4. Atualize componentes que consomem
5. Atualize docs/API_CONTRACTS.md

Parte 2: Forçando Padrões com Hooks (Garantias, não sugestões)

Por que regras textuais falham

A documentação oficial da Anthropic é clara: "Prompts are great for suggestions; hooks are guarantees." Regras no CLAUDE.md são sugestões que o modelo pode ignorar. Hooks são scripts que RODAM — é código, não conversa.

Hook 1: Post-Edit — Auto-format após cada edição

.claude/hooks/post-edit.sh :

#!/bin/bash
# Roda Prettier em arquivos .tsx/.ts/.css após edição
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

if [[ -z "$FILE_PATH" ]]; then exit 0; fi

# Só formata arquivos do projeto
if echo "$FILE_PATH" | grep -qE '\.(tsx?|css)$'; then
  npx prettier --write "$FILE_PATH" 2>/dev/null
fi

exit 0
Hook 2: Pre-Edit — Bloqueia padrões proibidos

.claude/hooks/pre-edit.sh :

#!/bin/bash
# Bloqueia edições que violam regras do projeto
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
CONTENT=$(echo "$INPUT" | jq -r '.tool_input.content // .tool_input.new_str // empty')

if [[ -z "$FILE_PATH" || -z "$CONTENT" ]]; then exit 0; fi

# Bloqueia hex hardcoded em .tsx (exceto components/ui/)
if echo "$FILE_PATH" | grep -qE '\.tsx$' && ! echo "$FILE_PATH" | grep -q 'components/ui/'; then
  if echo "$CONTENT" | grep -qE '#[0-9a-fA-F]{3,8}[^-]'; then
    echo "BLOQUEADO: Cor hex hardcoded detectada em $FILE_PATH. Use classes Tailwind ou CSS variables." >&2
    exit 2
  fi
fi

# Bloqueia import de lucide-react fora de components/ui/
if echo "$FILE_PATH" | grep -qE '\.tsx$' && ! echo "$FILE_PATH" | grep -q 'components/ui/'; then
  if echo "$CONTENT" | grep -q 'lucide-react'; then
    echo "BLOQUEADO: Import de lucide-react fora de components/ui/. Use <Icon name=\"...\"> do HugeIcons." >&2
    exit 2
  fi
fi

# Bloqueia SVG inline em componentes custom
if echo "$FILE_PATH" | grep -q 'components/custom/'; then
  if echo "$CONTENT" | grep -qE '<svg[ >]'; then
    echo "BLOQUEADO: SVG inline em componente custom. Use <Icon name=\"...\">." >&2
    exit 2
  fi
fi

exit 0
Hook 3: Quality Gate — Roda no fim de cada turno

.claude/hooks/quality-gate.sh :

#!/bin/bash
# Roda typecheck rápido no fim de cada turno do Claude
cd "$CLAUDE_PROJECT_DIR" || exit 0

# TypeScript check (falha rápida, não o build completo)
ERRORS=$(npx tsc --noEmit --pretty false 2>&1 | head -20)
if [ $? -ne 0 ]; then
  echo "⚠️ TypeScript errors detectados:" >&2
  echo "$ERRORS" >&2
  exit 2  # Força o Claude a corrigir antes de continuar
fi

exit 0

O que esses hooks garantem:

  • Formatação consistente SEM depender do Claude lembrar
  • Bloqueio FÍSICO de padrões proibidos (hex hardcoded, lucide-react, SVG inline)
  • TypeScript valida a cada turno — erros de tipo são pegos imediatamente

Parte 3: Eliminando Gaps Frontend ↔ Backend

O problema real: Contratos inexistentes

Quando o front usa { userName: string } e o back retorna { user_name: string }, o teste unitário passa (porque testa contra mock errado), mas a integração quebra. Isso é um problema de contrato , não de teste.

Solução: Contract-First Development
types/api/
├── venda.ts          # Schema da entidade Venda
├── afiliado.ts       # Schema da entidade Afiliado
├── carrinho.ts       # Schema da entidade Carrinho
├── pedido.ts         # Schema da entidade Pedido
├── cobranca.ts       # Schema da entidade Cobrança
└── index.ts          # Barrel export

Workflow de sync front↔back
1. Backend define/muda endpoint
   ↓
2. Cristiano atualiza types/api/[entidade].ts  ← CONTRATO
   ↓
3. pnpm typecheck quebra onde precisa mudar     ← ENFORCEMENT
   ↓
4. Frontend atualiza hooks, componentes, mocks  ← CASCATA
   ↓
5. pnpm build passa                             ← VALIDAÇÃO

Slash command para automatizar: .claude/commands/sync-api.md 

Quando um endpoint de API mudar:

1. Leia o arquivo types/api/ correspondente à entidade
2. Pergunte: "O que mudou na API?" 
3. Atualize o tipo em types/api/
4. Rode: pnpm typecheck
5. Para CADA erro de tipo, corrija o arquivo apontado
6. Rode: pnpm typecheck novamente até passar
7. Atualize o mock correspondente em __mocks__/
8. Rode: pnpm build
9. Atualize docs/API_CONTRACTS.md com a mudança e a data

$ARGUMENTS contém a entidade que mudou (ex: "venda", "afiliado")

Parte 4: Documentação Viva — Como Manter Atualizado

O problema de "docs ficam velhos"

Docs ficam desatualizados quando atualizar é um passo manual separado. A solução: fazer a doc ser parte do workflow, não um extra.

Strategy 1: CHANGELOG.md como hábito de commit

Adicione ao CLAUDE.md:

## Commits
- Após cada feature/fix, adicione uma linha em docs/CHANGELOG.md
- Formato: `- [YYYY-MM-DD] [módulo] Descrição curta da mudança`
Strategy 2: DECISIONS.md (Architecture Decision Records)
# Decisões de Arquitetura

## ADR-001: Ícones via HugeIcons CDN (não Lucide)
- **Data:** 2026-02-15
- **Status:** Aceita
- **Contexto:** Lucide era usado no e-commerce, mas o admin precisa de set mais amplo
- **Decisão:** HugeIcons stroke-rounded via CDN, componente <Icon> wrapper
- **Consequências:** Componentes shadcn/ui mantêm Lucide internamente. No app, só HugeIcons.

## ADR-002: Contract-First para APIs
- **Data:** 2026-02-26
- **Decisão:** types/api/ é fonte de verdade. Front e back sincronizam por esses tipos.
- **Consequências:** Mocks derivam dos tipos. TypeScript pega divergências em compilação.

Parte 6: Anti-patterns a Evitar

❌ O que NÃO fazer
Anti-pattern Por que falha O que fazer
CLAUDE.md com 300+ linhas Modelo ignora metade Podar para ≤100, mover resto para rules/
"Use shadcn" sem exemplos Vago demais, modelo adivinha Apontar arquivo específico como referência
Docs separados do código Ninguém atualiza Types como contrato, hooks como enforcement
Corrigir o mesmo erro 3x Contexto poluído com falhas /clear + reescrever prompt melhor
Mock com dados inventados Não bate com API real Mock tipado que deriva de types/api/
Regras apenas como texto Sugestão, não garantia Hooks para enforcement determinístico
Nunca atualizar CLAUDE.md Mapa desatualizado Revisar a cada sprint/quinzena
@file para embedar docs Consome contexto toda sessão "Para X, consulte docs/X.md"
✅ Regras de ouro
  1. Se o Claude erra a mesma coisa 2x, é problema de contexto, não do Claude. Adicione uma rule ou um hook.
  2. CLAUDE.md é para o que é universal. Rules para o que é scoped. Hooks para o que é inegociável.
  3. Docs que não são referenciados automaticamente não existem. Conecte docs ao workflow via hooks e types.
  4. TypeScript é seu melhor linter de integração. Se front e back compartilham tipos, divergências viram erros de compilação.
  5. Sessões curtas > sessões longas. /clear entre features. Contexto limpo = resultado melhor.
