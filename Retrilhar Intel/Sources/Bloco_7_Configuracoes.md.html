Tarefa 1 — Usuários

Título: [RETRILHAR] [CONFIG] Usuários Status: BACKLOG Tags: media · fluxo

Descrição

OBJETIVO Gestão de usuários internos da empresa. Lista com ações de edição, desativação, reenvio de convite e reset de senha. Convite é feito por e-mail com definição do perfil de acesso. HISTÓRICO DE DECISÕES E MUDANÇAS

  • Escopo §8.1 explicita: "Revisar fluxo atual de autocadastro (reclamação de cliente)" — há insatisfação reportada com o fluxo existente de autocadastro de usuários. Precisa de investigação e refinamento.
  • Escopo define lista com colunas: nome, e-mail, perfil, status, último acesso.
  • Escopo define ações inline: editar, desativar, reenviar convite, resetar senha.
  • Modal "Convidar Usuário" com campos: e-mail, perfil de acesso (select), mensagem personalizada (opcional). Ao enviar, usuário recebe e-mail com link para criar senha e completar cadastro. OBSERVAÇÕES
  • Convite de usuário interno aqui é distinto do convite de Vendedor/Afiliado (Bloco 5, Tarefa 4) — usuário interno tem acesso a múltiplos módulos conforme perfil, vendedor/afiliado é perfil específico com interface limitada.
  • Reset de senha de usuário ativo força relogin — é ação destrutiva na prática.
  • Desativação de usuário com histórico de ações: histórico precisa permanecer no log de auditoria (RPP002 §3.2 reforça importância do log). BLOQUEIOS
  • Qual é a reclamação específica sobre o fluxo atual de autocadastro? Precisa ser investigada antes de desenhar.

Tarefa 2 — Perfis de Acesso

Título: [RETRILHAR] [CONFIG] Perfis de Acesso Status: BACKLOG Tags: media · fluxo

Descrição

OBJETIVO Configuração da matriz de permissões do sistema. Cada perfil define o que pode fazer em cada módulo (visualizar, criar, editar, excluir). Controla acesso a dados sensíveis (saúde, financeiro) e operações destrutivas. HISTÓRICO DE DECISÕES E MUDANÇAS

  • Escopo §8.1 define perfis base: Gestor, Operador, Financeiro, Marketing, Vendedor, Admin.
  • Escopo: edição de perfil inclui nome, lista de permissões por módulo (checkbox: visualizar, criar, editar, excluir), módulos que o perfil pode acessar.
  • Escopo: "Matriz de permissões será definida durante o projeto" — não há matriz concreta ainda.
  • RPP002 §3.2, §3.4 e §3.5 fazem referências cruzadas a "Módulo 14.1 — Perfis de Acesso" quando tratam de: Bloco de Saúde com acesso restrito (§3.2), Ficha 4 de Dados de Saúde com acesso restrito (§3.4), Líder de Operação sem dados financeiros (§3.5). OBSERVAÇÕES
  • Este módulo é pré-requisito para várias regras de negócio de outros módulos — especialmente Agenda (Participantes, Listas, Painel do Líder) e Vendas (Detalhes do Pedido).
  • Duplicar perfil é útil para criar variantes (ex: "Gestor Júnior" a partir de "Gestor" removendo algumas permissões).
  • Granularidade das permissões (4 ações × N módulos) gera matriz potencialmente grande — UI precisa de agrupamento visual. BLOQUEIOS
  • Matriz de permissões concreta: quais são as combinações padrão dos 6 perfis base? Escopo diz que "será definida durante o projeto" — precisa ser decidida antes de implementar o motor de permissões.
  • Permissões especiais (acesso a saúde, a dados financeiros): são flags separadas da matriz principal ou fazem parte dela?
  • Alteração de permissões em tempo real: aplica imediatamente ou precisa do usuário relogar?
Caminho principal

  • [ ] Edição de perfil (nome, matriz de permissões)
  • [ ] Matriz de permissões (visualizar, criar, editar, excluir por módulo)
  • [ ] Seleção de módulos acessíveis pelo perfil
  • [ ] Duplicar perfil
  • [ ] Flag especial "Acesso a dados de saúde"
  • [ ] Flag especial "Acesso a dados financeiros"
  • [ ] Adaptar fluxo para mobile

  • [ ] [exceção] Alteração de permissões em tempo real (impacto imediato ou após relogin)
  • [ ] [exceção] Remoção de permissão de Admin — bloqueio (precisa de pelo menos um Admin)

Tarefa 3 — Templates de Mensagem

Título: [RETRILHAR] [CONFIG] Templates de Mensagem Status: BACKLOG Tags: media · fluxo

Descrição

OBJETIVO Biblioteca de templates de comunicação (WhatsApp e E-mail) disparados automaticamente pelo sistema em momentos específicos (confirmação de compra, lembrete de atividade, pesquisa de satisfação, recuperação de carrinho). HISTÓRICO DE DECISÕES E MUDANÇAS

  • Escopo §8.2 define templates por gatilho: confirmação de compra, lembrete de atividade, pesquisa de satisfação, recuperação de carrinho.
  • Escopo define editor: assunto (para e-mail), corpo da mensagem, tags dinâmicas disponíveis ({nome}, {produto}, {data}, {horario}, {link_pagamento}, etc.), preview. OBSERVAÇÕES
  • Editor de template aqui é reutilizável em outros contextos: pesquisa de qualidade (CRM §4.3), termos e políticas (§8.3), templates de contrato (Módulo 5). Vale construir editor genérico de "texto rico + tags + preview".
  • Gatilhos de envio são integrações com outros módulos — definição de quando cada template é disparado vem de Vendas (carrinho abandonado), Agenda (lembrete de atividade), CRM (satisfação).
  • Testar envio (para o próprio gestor) é importante para validar antes de ativar em produção. BLOQUEIOS
  • Envio de WhatsApp depende de integração com provider (WhatsApp Business API ou similar). Qual provider? Aguardando decisão — ver Tarefa 5 (Integrações).
  • Templates podem ter múltiplas versões (ex: teste A/B)? Ou cada gatilho tem uma versão única?

Tarefa 4 — Termos e Políticas

Título: [RETRILHAR] [CONFIG] Termos e Políticas Status: BACKLOG Tags: media · fluxo

Descrição

OBJETIVO Biblioteca de templates legais que são vinculados a produtos (política de cancelamento, termo de responsabilidade, termo de uso de imagem). Cliente aceita esses termos na hora da reserva com validade jurídica (IP, hash, timestamp). HISTÓRICO DE DECISÕES E MUDANÇAS

  • Escopo §8.3 define templates-base: Política de Cancelamento, Termo de Responsabilidade, Termo de Uso de Imagem.
  • Escopo: editor igual ao de contratos (texto rico + tags).
  • Escopo: vincular template a produtos específicos ou usar como padrão.
  • RPP002 §3.2 (Detalhes Completos da Reserva) reforça importância jurídica: aceite digital tem IP do dispositivo, hash do documento, timestamp. Botão de download em PDF com validade jurídica. OBSERVAÇÕES
  • Editor é o mesmo de Templates de Contrato (Módulo 5) — padronizar o componente.
  • Versionamento é crítico: se o termo muda, reservas antigas mantêm referência à versão aceita no momento da compra.
  • Template pode ser "padrão" (aplica a todos os produtos sem vínculo específico) ou "específico" (vinculado a um ou mais produtos). BLOQUEIOS
  • Versionamento de termos: como tratar? Cada alteração vira nova versão automaticamente? Permite editar em rascunho antes de publicar?
  • Conflito de termos: se um produto tem termo específico E existe termo padrão, qual prevalece? (escopo parece dizer "específico sobrescreve padrão", mas vale confirmar).
Caminho principal

  • [ ] Editor texto rico + tags (reutiliza componente de Templates de Contrato)
  • [ ] Preview preenchido com dados de exemplo
  • [ ] Vincular template a produtos específicos
  • [ ] Usar template como padrão (aplica a todos os produtos sem vínculo específico)
  • [ ] Duplicar template
  • [ ] Versionamento (publicar nova versão, manter histórico)
  • [ ] Adaptar fluxo para mobile
Edge cases

  • [ ] [exceção] Alteração de template com aceites ativos (reservas existentes mantêm versão antiga)
  • [ ] [exceção] Produto sem termo vinculado — usa padrão se existir, senão alerta
  • [ ] [destrutivo] Exclusão bloqueada quando vinculado a produto com reservas
  • [ ] [erro] Template com tag inválida — validação inline
  • [ ] Adaptar edge cases para mobile
